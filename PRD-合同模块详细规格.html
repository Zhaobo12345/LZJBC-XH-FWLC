1.7 数据展示规则
撤回合同：标识并保留（列表示例）

PC 端合同审核管理列表对「提交平台审核后撤回」与「变更发起后撤回」的合同，不删除、不隐藏，而是以灰色标签行保留，仅供审计留痕：

  • 合同已撤回（status：contract_withdrawn）：发起方在平台审核（platform_reviewing）前撤回提交，合同回退拟定中（draft），平台不再审核。
  • 变更已撤回（status：change_withdrawn）：发起方在平台审核（change_platform_reviewing）前撤回变更申请，变更取消、合同恢复已签约（signed）。

展示特征：状态标签灰底灰字（.status-tag.withdrawn，#F5F5F5 / #8C8C8C）；操作区仅「查看」（只读，进入详情页 status=withdrawn），无「去审核」；状态筛选器提供「合同已撤回 / 变更已撤回」选项。

示例演示数据（见 1.5 操作按钮矩阵 末两行）：基础施工服务合同-雁塔区撤回示例（合同已撤回）、设计服务合同-未央区撤回示例（变更已撤回）。

同一合同多次变更：始终一条数据

列表以合同为维度，每个合同仅占一行：

  • 同一合同无论发起多少次变更，列表不派生多行；行内「当前状态」反映其当前最新待审态（如处于变更审核中则显示 changing / change_platform_reviewing）。
  • 多次变更的全部历史（含已通过 / 已驳回 / 已撤回）在合同详情页「变更记录」选项卡 按时间倒序逐条枚举（见 5.11 变更记录生成），不在列表层展开。
  • 示例：某合同已签约后发起 3 次变更（2 次通过、1 次撤回），列表仍仅 1 行，状态随最近一次变更流转；详情页「变更记录」选项卡 显示该 3 条变更流水。

2.7 状态详解（按状态）

本节按状态（及同界面处理的状态组）逐一说明其 功能与可见模块 / 状态相关字段 / 操作项 / 交互流程。跨状态通用的交互流程统一见 2.8. 统一交互流程。

2.7.1 平台审核中（platform_reviewing）

功能与可见模块：状态横幅显示"⏳ 待平台审核"；审核操作区（#statusReviewActions）显示，含「驳回」「审核通过」按钮；主内容区（概览 / 合同正文 / 阶段任务 / 变更记录）为只读；变更相关横幅与高亮均隐藏；右侧「操作记录」时间线始终可见。

状态相关字段：无基础字段新增；点击「驳回」后弹出驳回弹窗（#rejectModal），含合同基本信息+驳回原因输入（confirmRejectFromModal，必填校验，1–500 字符）。

操作项：

  • 驳回（showRejectInput → #rejectModal弹窗 → confirmRejectFromModal校验 → confirmModal二次确认 → switchStatus）：展开原因输入区，按钮文案变为"取消驳回"，并显示「确认驳回」（pc-btn-danger）。原因校验通过后二次确认，切换至 reviewed_reject。
  • 审核通过（approveContract）：二次确认后切换至 reviewed_pass。

交互流程：见 2.8. 统一交互流程（审核通过 / 审核驳回）。

2.7.2 变更审核中（change_reviewing）

功能与可见模块：与平台审核中一致，额外显示：变更原因横幅（#changeReasonBanner）、合同正文变更高亮（#contractPriceChange 旧值/新值对比 + #contractAdditionChange 新增条款）、阶段任务区变更摘要卡片（#changeSummaryCard）+ 阶段2变更徽标 + 阶段3新增（#stage3NewSection）/原阶段（#stage3OriginalSection）；「变更记录」选项卡 显示当前变更记录（#changeRecord1）。

状态相关字段：变更原因（#changeReasonBanner 静态展示）、变更价款对比（#contractPriceChange）、新增条款（#contractAdditionChange）。

操作项：审核面板同平台审核中（驳回 / 审核通过），文案针对"变更"——审核通过切换至 change_reviewed_pass，驳回切换至 change_reviewed_reject。

交互流程：同审核流程，nextStatus 使用变更态（见 2.7.6）。

2.7.3 审核 / 变更驳回态（reviewed_reject · change_reviewed_reject）

二者界面处理相同（均显示驳回原因横幅），仅配置横幅文案不同：

状态横幅标题（statusConfig）变更记录标记
reviewed_reject❌ 审核已驳回—
change_reviewed_reject❌ 变更已驳回已驳回

功能与可见模块：状态横幅显示对应驳回文案；驳回原因横幅（#rejectReasonBanner，由 updateRejectReasonBanner 控制，覆盖上述两态 reviewed_reject / change_reviewed_reject）显示驳回原因（#rejectReasonContent）；审核操作区隐藏。

状态相关字段：驳回原因（#rejectReasonContent，文本，由驳回时写入）。

操作项：无（退回修改由服务方在小程序端进行）。

交互流程：由 2.7.1 / 2.7.2 的"驳回"操作进入。

2.7.4 审核通过（reviewed_pass）与 变更通过（change_reviewed_pass）

功能与可见模块：状态横幅显示"✅ 审核已通过 / ✅ 变更已通过"；审核操作区隐藏；变更通过态下变更记录显示"已生效"、阶段任务变更落地（#changeSummaryCard / #stage3NewSection 保持显示）。

状态相关字段：无。

操作项：无。

交互流程：由审核 / 变更审核的"审核通过"进入。

2.7.5 已撤回（withdrawn）

功能与可见模块：状态横幅显示"↩ 已撤回"（灰渐变，.status-banner.withdrawn），文案"该合同/变更已被发起方撤回，平台不再审核"；审核操作区隐藏；主内容区（概览 / 合同正文 / 阶段任务 / 变更记录）只读；右侧「操作记录」时间线始终可见。该状态仅从 PC 列表「查看」按钮进入（URL 带 status=withdrawn 与 wtype=contract|change，由 withdrawType 区分撤回类型）。

状态相关字段：撤回类型 wtype（contract = 合同提交平台审核前撤回；change = 变更申请平台审核前撤回）。

操作项：无（只读审计态，无审核 / 编辑操作）。

操作记录（#operationLog）撤回节点：按 wtype 区分——

  • 撤回合同（contract）：进入平台审核（系统）→ 撤回合同（陈庄，附"发起方在平台审核完成前主动撤回，平台不再审核"）→ 合同审核终止（系统）。
  • 撤回变更（change）：合同审核通过（运营人员）→ 发起变更申请（陈庄）→ 撤回变更申请（陈庄，附"发起方在平台审核前主动撤回本次变更，变更流程已终止"）→ 变更审核终止（系统）。

变更记录（#changesContent）撤回表现：

  • 撤回变更（change）：复用「第一次变更」记录（#changeRecord1），状态徽标与正文「变更状态」均置为「已撤回」（灰，.change-record-status.withdrawn），隐藏其余变更记录。
  • 撤回合同（contract）：隐藏全部变更记录，#noChangeRecord 显示"合同已被发起方撤回，暂无变更记录"。
2.8 统一交互流程
2.8.1 审核通过流程
1. 运营人员点击审核面板中"审核通过"按钮（pc-btn-primary） 2. 弹出确认弹窗（#confirmModal）：标题"确认审核通过"（变更审核时为"确认审核通过变更"），描述合同将进入待确认状态 3. 用户点击"确定" → switchStatus(nextStatus) - 合同审核：nextStatus = reviewed_pass - 变更审核：nextStatus = change_reviewed_pass 4. 审核面板隐藏 → 状态横幅保持显示 → 状态操作区无按钮 5. 操作日志（#operationLog）追加"合同审核通过"记录 6. 轻提示 反馈："审核通过，合同已进入待确认状态"
2.8.2 审核驳回流程
1. 运营人员点击审核面板中"驳回"按钮（showRejectBtn，pc-btn-default） 2. 驳回原因输入区（#rejectReasonInput）展开，按钮文案变为"取消驳回" 3. 确认驳回按钮（confirmRejectBtn，pc-btn-danger 样式）显示 4. 用户输入驳回原因（textarea #rejectReason） 5. 点击"确认驳回" → 校验驳回原因： - 校验：Validation.validate.textLength(reason, 500, true, "驳回原因") - 空值 轻提示错误 → 驳回原因必填，1-500 字符 6. 校验通过 → showConfirmModal("确认驳回", "确定驳回该合同吗？...") 7. 确认 → switchStatus(nextStatus) - 合同驳回：nextStatus = reviewed_reject - 变更驳回：nextStatus = change_reviewed_reject 8. 驳回原因写入 rejectReasonContent → rejectReasonBanner 展示 9. 轻提示 反馈："已驳回，合同退回修改状态"
2.8.3 变更审核附加逻辑
变更审核（change_reviewing）与合同审核（platform_reviewing）共用同一审核面板，差异如下： - 审核面板标题：platform_reviewing 时为 "🔍 合同审核"，change_reviewing 时为 "🔍 变更审核" - change_reviewing 附加显示：变更原因横幅（#changeReasonBanner）+ 合同正文变更高亮（contractPriceChange: 旧值/新值对比 + contractAdditionChange: 新增条款） - 阶段任务区显示变更摘要卡片（#changeSummaryCard）+ 新增阶段（stage3NewSection，标记"新增"badge）+ 已修改任务/阶段标记 - 变更记录 选项卡：change_reviewing / change_reviewed_pass 显示当前变更记录（#changeRecord1） - 审核通过/驳回后的 nextStatus：均使用 change_reviewed_pass / change_reviewed_reject

3.5.2.2 更换阶段任务模板（详细交互）

在「阶段任务」选项卡 内，顶部操作区的「更换任务模板」按钮（即 3.5.3 所述"选择模板"入口，对应 draftTemplateBtn（原型位置）；仅在合同正文 / 阶段任务 选项卡 显示，附件 选项卡 自动隐藏该按钮）用于一键套用平台预设的、与当前合同匹配的阶段任务结构。点击后进入如下完整流程：

  1. 打开选择弹窗：showDraftTemplatePicker() 依据 state.draftContentTab 判定当前为 stage-task，转调 showStageTemplatePicker() 打开 stageTemplateModal 底部抽屉弹窗（遮罩层 + 锚定底部的卡片，含 ✕ 关闭按钮与底部「取消」按钮；与预览弹窗同款风格）。
  2. 模板匹配筛选（同城市 + 同合同类型）：renderStageTemplateList() 从 stageTemplates 中过滤出 city === '西安' && type === '水电工程' 的模板（演示合同所在城市与合同类型，实际以当前合同数据为准）。每个模板项展示：
    · 名称、描述；
    · 元信息标签：N个阶段、城市；
    · 右侧操作：「预览」「使用」两个按钮。
    若无任何匹配模板，显示 stageTemplateEmpty 空态提示"暂无匹配的阶段任务模板"。
  3. 预览（点击「预览」）：previewStageTemplate(id) 不关闭选择弹窗，而是以选择弹窗的上层（下钻视图）形式打开 templatePreviewModal（底部抽屉，与选择弹窗同款风格）：
    · 头部：模板名称、类型、城市、更新时间；
    · 主体「阶段任务明细」：逐阶段渲染「阶段序号 + 阶段名称」，其下逐条列出「任务名称」（任务项左对齐排布），可滚动查看完整结构（与 PC 端阶段任务模板字段一致，不包含金额字段）；
    · 底部按钮：「取消」（closeTemplatePreviewModal，关闭预览、回到选择弹窗、不改动当前内容）、「使用此模板」（applyTemplateFromPreview，等价"使用"，见下，并同时关闭预览与选择弹窗）。
  4. 预览返回（关闭预览）：关闭 templatePreviewModal 后选择弹窗自然透出（预览为选择弹窗的上层，关闭后返回「更换模板」选择弹窗，可继续对比其它模板或重新决定），而非直接回到详情页——避免丢失选择上下文、需重新打开弹窗。
  5. 使用 / 替换当前内容（点击「使用」或预览内「使用此模板」）：applyStageTemplate(tpl)（「使用」直接经 applyStageTemplateDirectly→applyStageTemplate；预览内「使用此模板」经 applyTemplateFromPreview→applyStageTemplate）将编辑区 #editStageList 的 innerHTML 整体替换为模板阶段任务结构：
    · 每个阶段渲染为与 3.5.2.1 默认草稿完全一致的 .stage-card（阶段名称输入框、按序执行开关、+ 添加任务 / × 删除阶段），任务渲染为 .task-edit-item（任务名称输入框、✎ 编辑 / × 删除）；整体结构、交互与默认阶段任务保持一致，不含金额字段；
    · 同时显示 stageTemplateInfo「已选择模板：X」标签及"模板内容可编辑调整"提示；
    · 顶部 轻提示「已应用模板：X」；
    · 关闭弹窗（预览内「使用此模板」同时关闭预览与选择弹窗；选择弹窗内「使用」关闭选择弹窗）。
    替换后系统仍在 3.5.2.1 的结构上继续支持增删改（模板内容可编辑调整）。
  6. 取消本次更换（点击「取消」/ 遮罩 / ✕）：选择弹窗底部「取消」、预览弹窗「取消」、点击遮罩层或 ✕ 关闭按钮，均仅调用 closeStageTemplatePicker / closeTemplatePreviewModal 关闭对应弹窗（预览关闭后回到选择弹窗），当前已有的阶段任务内容保持不变，即本次更换模板被取消。

注：关于"点击使用是否弹窗二次确认"——当前原型中「使用 / 使用此模板」为直接替换 + 轻提示 反馈（不做独立确认弹窗），替换即时生效、且替换后仍可编辑调整，误替换代价低；同时替换只覆盖"阶段任务"结构、不影响同页合同正文与附件。如需在替换前增加"确认覆盖当前阶段任务？"的二次确认弹窗，属原型交互增强，可另行评估。合同文本模板（合同正文 选项卡）的更换交互同此机制，入口为 showTemplatePicker()，对应 templateModal / 预览弹窗。

3.5.4 草稿暂存（仅保存）功能

在"拟定中"类（draft / draft_submittable）及"平台审核驳回"类（platform_rejected / platform_rejected_modified）可编辑状态下，编辑合同内容过程中可随时点击「仅保存」将当前表单内容暂存到本地（localStorage 草稿快照），而不触发提交 / 重新提交流程。目的是避免编辑到一半、尚未满足提交条件时内容丢失，提升移动端编辑体验。

· 内容已完善，发起方（draft_submittable）

  • 执行人提醒（微信服务号通知 · 权威规则 · 非工人合同与工人合同通用）：合同进入可施工态（signed / worker_signed）后，系统为该合同下「已配置执行人且处于待开始（含前置阻塞）」的任务，通过微信服务号通知向对应执行人推送「任务执行」提醒（不再生成应用内「合同任务执行」待办，该待办类型已按最新规则取消）；触发时间 = 合同签约时间。细则：
    • ⚠️ 任务锁定（签约前）（重要）：合同处于「已确认（confirmed / worker_confirmed）」及之前态时，合同下任务锁定、不支持任何执行操作——即使任务已提前配置执行人并流转至「待开始」，执行人也无法提交完成 / 上传执行记录、确认人也无法确认，系统不向执行人发送任何提醒。提醒须等待合同「已签约」解除锁定后才发送。非工人合同与工人合同均遵守此约束（工人合同见 §7.5.3.4）；变更期间的同类锁定见 第五章 变更期间任务锁定规则。
    • 签约一次性提醒：合同由「已确认」→「已签约」后，系统扫描该合同下全部「已配置执行人 + 待开始」的任务，向每位执行人发送微信服务号通知（覆盖签约前已配置执行人、受前置约束尚未提醒的任务）。
    • 可施工态下补配置：若合同已处于「已签约」，后续才为某「待开始」任务配置执行人，任务流转至「待开始」时同步向该执行人发送微信服务号通知（与签约扫描同一逻辑，避免遗漏）。
    • 提醒归属与去重：提醒仅触达该任务执行人，同一任务在可施工态下仅发送一次；通知口径、触发规则与跳转目标见 《PRD-完整文档》§7.10 服务通知。

合同处于「已签约」后，当该合同下全部有效任务（未被软删除）均为「已完成」时，详情页状态横幅在「已签约」文案旁叠加绿色「已履约完成」标识。该标识为实时派生（无持久化状态、不入合同状态机）：任一任务被驳回回流 / 转回未完成，标识自动消失。

  • 判定：合同状态 ∈ 已签约及变更各态（signed / worker_signed / 变更态），且合同下全部有效任务状态均为「已完成」。
  • 呈现位置：① 合同详情页状态横幅「已签约」旁绿色徽标「已履约完成」；② 项目详情「合同概览」该合同行叠加「已完工」角标；③ 合同列表卡片状态列叠加「已履约完成」。
  • 不阻断操作：履约完成不改变操作权限，已签约态仍可「发起变更」；任务驳回回流时标识自动消失（与任务状态实时联动）。
  • 原型演示：合同详情页右侧导航「签约阶段」提供「已签约（已履约完成）」演示项，一键置全部任务为已完成并触发徽标。
⚠️ 重要：合同任务「锁定 → 解锁」统一规则（签约前 / 变更期间）

合同下任务的可执行性由合同状态闸门控制，存在两类锁定，解锁后才允许执行 / 确认并向执行人发送微信服务号通知提醒：

  • ① 签约前锁定：合同处于「已确认」及之前态，任务锁定，即使已配执行人也不支持执行 / 确认、不向执行人发送提醒；进入「已签约」后解锁（本页 §3.10.14）。
  • ② 变更期间锁定：合同发起变更后，全周期变更态下任务锁定，不支持执行 / 确认、不生成新待办；变更失败（驳回 / 撤回）或成功（生效）到达终态后解除锁定（第五章 变更期间任务锁定规则）。

两类锁定本质一致（仅触发态不同），均禁止执行 / 确认且不向执行人发送提醒；非工人合同与工人合同通用。

变更流程相关状态（变更中 / 待确认变更 / 变更审核中 / 变更审核驳回 / 变更确认中 / 变更签约中 / 变更已生效）及各变更页面说明已统一收录于第五章：5.15 各变更状态页详述（5.15.1–5.15.8），每节包含原型链接、适用方/视角、横幅文案、进入条件、页面结构、底部按钮、状态流转、关键交互逻辑与字段规格。为避免与第五章重复，本章不再另列变更态子节，请以第五章为权威出处核对变更态页面细节。

⚠️ 变更期间任务锁定规则（通用 · 非工人合同与工人合同均适用）
发起变更即锁定，到达终态才解锁

合同由「已签约」发起变更后，合同下全部阶段任务进入锁定状态：执行人不可提交完成 / 上传执行记录，确认人不可确认，且锁定期间不生成新的执行人待办。锁定持续覆盖变更全周期，直至变更到达终态方才解锁：

  • 锁定区间（变更全周期）：自发起方点击「发起变更」起，经 变更中（changing）/ 变更审核中（change_platform_reviewing，仅涉及金额 / 正文 / 附件变更的非工人合同）/ 待确认变更（change_confirming）/ 变更确认中（change_confirming_sender / change_confirming_receiver）/ 变更签约中（change_signing_wait）等中间态，直至终态。
  • 变更失败 → 解锁（原 V1 继续执行 / 确认）：变更被驳回（change_platform_rejected / change_rejected）或发起方撤回（change_withdrawn）后，合同恢复「已签约（signed / worker_signed）」，任务解除锁定并按原 V1 版本继续执行 / 确认；期间暂停的任务自解锁时刻恢复流转。
  • 变更成功 → 解锁（基于 V2 重新执行 / 确认）：变更生效（change_confirmed）后，任务解除锁定并按 V2 版本恢复流转；变更项任务的执行人提醒按 §5.15.8 发送（作用域限定为变更项）。
  • 与签约前锁定的关系：本规则是「任务锁定」的变更态延伸，与 §3.10.14 任务锁定（签约前） 同属锁定语义，区别仅触发态不同（签约前 vs 变更全周期）；两类锁定均禁止执行 / 确认且不向执行人发送提醒，非工人合同与工人合同通用。

接受邀约后的成员登记与权限分配

受邀方点击「确认加入」（即在整页接单卡片流页面的接单动作）并成为合同乙方；系统将其自动加入合同所属架构层级（group 字段更新）、登记入项目成员名册（若此前尚未在册则新增为项目成员）的同时，会同步完成权限分配，包含以下三层：

① 项目成员名册登记：合同甲方 / 乙方候选人均须从「项目成员」中筛选（见 §3.5.1 拟定中编辑表单 · 签约双方），故成为本合同乙方的同时，系统将该工人登记入项目成员名册——若其此前未在项目成员列表中，则自动新增为项目成员；若已在册则仅更新其架构层级与乙方身份的关联。其项目成员身份与乙方身份、架构层级归属一并纳入成员关系管理。仅首位确认者（首胜者）登记入项目成员并成为乙方；其余受邀方（抢单失败 / 已拒绝）因未成为乙方，不触发项目成员登记。

② 架构层级基础权限：该工人作为成员被纳入合同所属架构层级（如「水电工程」），随即持有该层级的基础数据权限——即「所属架构及下属层级权限（含合同）」（权限模型见 §2.9 / §5.12 权限控制，以及基础施工服务合同 §3 合同金额展示受权限控制规则）；可在该架构子树内查看并参与项目数据，合同金额按其有权限规则展示实际金额（不再脱敏为 ***）。

③ 乙方（party B）对应权限：系统为该工人绑定本合同的乙方身份权限，使其可查看本合同详情、接收并查看「乙方待确认 / 待签约」等乙方相关待办、参与本合同阶段任务的执行与确认流转；若处于变更流程，则作为乙方确认 / 驳回变更（详见 第九章）。

上述成员登记、权限与架构层级归属随乙方身份的变化而同步调整：发起方「撤回邀约」「恢复原乙方」或本受邀方「抢单失败 / 已拒绝」时，相应乙方身份与权限自动回收；因本次接单而新增的项目成员，在失去乙方身份后默认保留为普通项目成员（仅解绑乙方与架构层级归属）。

7.6 拟定中状态-编辑交互规格

工人合同进入 初始拟定（原型页 worker-contract-draft-initial-new.html）或 撤回后拟定（worker-contract-detail.html?status=worker_draft）时，合同详情页以「拟定中」展示，且直接显示可编辑面板（参考「合同详情（合规版）」§3.5），无需额外点击「编辑合同」按钮。两者共用同一状态 key worker_draft。创建合同成功后即落在此态——需先在此完善合同名称 / 金额 / 工期 / 违约责任、合同正文、阶段任务、附件、意向乙方等具体信息，经必填校验通过后方可「提交并邀请乙方」，再进入确认 / 签约流程。两种草案态共用同一编辑面板。

7.6.1 拟定中编辑面板（draftContentWrap）

📌 编辑 / 添加任务 · 执行人默认值规则（工人合同）

打开「编辑任务」弹窗时，若任务原本无执行人，系统按乙方选取阶段推导「执行人」字段默认值（仅对原本无执行人的任务生效、已有执行人不覆盖；不改变「执行人可空」字段属性、不强制必填）；执行人可选范围为项目内全部人员（项目成员搜索下拉：业主 / 设计师 / 项目总 / 工长 / 各工种人员等，点击「请选择执行人」即展开可选列表）。工人合同乙方为「意向乙方候选 1~3 人 + 最终乙方 1 人」的两段式，默认值推导分两种情形：

  • 拟定中 / 邀请中（partyBName 尚未确定，按意向乙方名单计数）：名单仅 1 人 → 默认填该意向乙方；名单为多人（2~3 人） → 最终乙方未定，执行人默认空、非必选（此时无法预判哪位会接单成为最终乙方）。
  • 已签约（partyBName 已确定，唯一 1 人）：默认填该最终乙方人员（与 §7.5.3.4「乙方确认接单→已签约：无执行人任务自动归属乙方」落地规则一致）。

「添加任务」弹窗同规则：打开添加任务弹窗时，「执行人」字段默认值按上述同一规则推导（意向名单仅 1 人或 partyBName 已确定 → 默认填该乙方；多人 → 默认空），默认值可修改 / 可清空，执行人仍非必填；可选范围与编辑任务一致，同为项目内全部人员。

确认人可选范围：「编辑任务」与「添加任务」弹窗的确认人均可选项目内全部人员（与执行人同源，项目成员搜索下拉），最多 5 人、选填；两弹窗规则一致。

「添加任务」与「编辑任务」弹窗内，执行标准与确认标准下方各设一处「工艺参考示例」配置区（3 列缩略图 + 标题 + ✎ 改标题 / × 删除 + 「＋ 添加」，最多 9 张、仅图片）。点击「＋ 添加」进入整页配置（从右滑入，自带状态栏 + 导航栏 + 底部固定保存栏），支持一次多选上传多张，满 9 张隐藏上传入口。任务行内不展示示例缩略图，示例只在任务详情（只读）弹窗与任务详情页展示；两组示例按「执行标准 → 执行示例 → 确认标准 → 确认示例 → 担责标准」顺序展示。完整规格见 11 工艺参考示例规格。

7.6.3 更换模板（按当前 选项卡 提供类型匹配模板）

点击「更换模板」按钮（draftTemplateBtn，原型位置；仅在合同正文 / 阶段任务 选项卡 显示，附件 选项卡 自动隐藏）按当前 选项卡 提供对应模板：正文模板（text）/ 阶段模板（stage）。模板列表仅显示与当前合同类型匹配的工种（如「水电班组服务合同」仅列水电类模板），每个模板项提供「预览」「使用」两个按钮。完整流程（对齐「合同详情（合规版）」§3.5.2.2）：

  1. 打开选择弹窗：showDraftTemplatePicker() 判定当前 选项卡 后转 openTemplatePicker(kind)，打开 wcTemplatePicker 底部抽屉弹窗（含 ✕ 与底部「取消」；与「合同详情（合规版）」更换模板选择弹窗同款风格）。
  2. 模板匹配筛选（按合同类型）：renderTemplatePickerList(kind) 过滤出与当前合同类型（typeName）匹配的模板（标准 / 精简两档），每项展示名称、描述、匹配说明。
  3. 预览（点击「预览」）：previewDraftTemplate(kind, id) 不关闭选择弹窗，以选择弹窗的上层（下钻视图）形式打开 wcTemplatePreview 预览弹窗——弹窗效果与布局对齐「拟定中（发起方）-新」（wcd-sheet 底部抽屉：标题 + ✕ / 元信息条「类型：X · 模板：Y（阶段模板为「阶段数：N」）」/ 内容区 / 纵向全宽「取消」「使用此模板」按钮）：阶段模板展示「阶段任务明细」——逐阶段「序号 + 名称 + 顺序/并行」，其下逐条「任务名称 + 执行 + 确认」（任务项左对齐排布，点击任务就地展开「执行 / 确认 / 担责标准」）；正文模板展示「违约责任」+「固定详细条款（不可修改）」，并注明甲乙方 / 合同金额 / 工期 等基础信息由合同主信息填写、不在固定条款内。底部「取消」（关闭预览、回到选择弹窗、不改动）/「使用此模板」（同时关闭预览与选择弹窗）。
  4. 预览返回（关闭预览）：关闭 wcTemplatePreview 后选择弹窗自然透出（预览为选择弹窗的上层，关闭后返回「更换模板」选择弹窗，可继续对比其它模板或重新决定），而非直接回到详情页。
  5. 使用 / 替换当前内容（点击「使用」或预览内「使用此模板」）：applyTemplate(kind, id)（预览内经 applyTemplateFromPreview→applyTemplate）将当前内容整体替换为模板结构：阶段模板以 STAGE_TEMPLATES[type].stages 覆盖 state.contract.stages（精简档取前 2 阶段）、重渲阶段任务区并展示「已选择模板：XX」标签；正文模板写入 contentIntro 与「已选择模板：XX」标签。替换后随编辑面板与内容区自动恢复，且仍可继续编辑调整。
  6. 取消本次更换（点击「取消」/ ✕ / 遮罩）：closeTemplatePicker / closeTemplatePreview 仅关闭弹窗，当前已有的合同正文 / 阶段任务内容保持不变。

注：工人合同「使用」为直接替换 + 轻提示「已应用模板」反馈（不做独立二次确认弹窗），替换即时生效、且替换后仍可编辑，误替换代价低；替换只覆盖当前 选项卡 对应内容（阶段模板仅改阶段任务、正文模板仅改合同正文），互不影响。合同文本模板与阶段任务模板各自独立标记「已选择模板」。阶段模板的数据来源与「合同详情（合规版）」§3.5.2.2 一致（同城市同类型匹配），差异在于工人合同按工种类型匹配、且任务字段含「执行 / 确认」归属（exec=工人、conf=陈庄）。

7.6.4 意向乙方选择（按工种过滤）
  • 草稿面板内「意向乙方」编辑区（inviteEditPanel），按合同类型过滤工种候选（TRADE_ROLE_BY_TYPE），可选 1–3 名意向乙方（仅六工种：拆除 / 水电 / 木作 / 泥瓦 / 油漆 / 小零工）。
  • 「仅保存」会持久化当前意向乙方选择；「提交并邀请乙方」时整体覆盖并发起邀约（confirmInvitation 具首胜校验，防并发重复确认）。
  • 撤回后 worker_draft 重选乙方：展示被替换原乙方历史卡片与提示，可就地修改后重提。
7.6.5 草稿暂存（仅保存）与提交校验

仅保存：将当前草稿编辑内容（合同名称 / 金额 / 工期 / 违约责任 / 意向乙方 / 合同正文 / 阶段任务 / 附件）经 patchContract 持久化到合约库，不改变合同状态、不发送邀约；重新进入拟定中时由编辑面板与内容区自动恢复（含意向乙方）。

提交并邀请乙方：patchContract 落库 + 向所选意向乙方发送邀约；含必填校验——合同名称非空、合同金额 > 0、违约责任非空、意向乙方已选（1–3 人）、至少存在一个阶段且至少一个任务（stageTaskOk）；未满足时轻提示具体缺失项（如「请填写合同名称」「请填写『违约责任』后再提交（必填项）」「请至少选择 1 名意向乙方」）。首位确认者成为合同乙方并使合同即时生效为已签约（首胜校验）。状态与操作详见7.5 状态机表「拟定中（初始）/ 拟定中（撤回后）」两行。

9.1 功能概述与定位

工人合同（班组服务合同）已签约后，仅发起方（工长·陈庄）可发起合同变更，受邀方（工人·乙方）只参与确认 / 驳回（不支持发起变更，其视角底部不出现「发起变更」按钮）。变更流程与合规版「发起变更功能」最大差异在于 去平台审核：双方确认即生效，无需平台介入。

与合规版发起变更的关键差异
  • 无需平台审核、无签约文件上传环节：发起方提交变更 → 受邀方确认 / 驳回，确认后即生成 V2 已签约生效，对比合规版需平台审核通过并上传签约文件。
  • 独立变更编辑整页：变更提案在独立整页 worker-contract-change.html 中填写（弹窗无法承载较多内容），非合规版的弹窗内编辑。
  • 生成 V2 版本：受邀方确认变更后合同即升级为 V2，原 V1 保留于「版本与流转」记录，可回溯。
  • 阶段任务暂停流转：变更期间（changing / change_confirming / change_confirming_sender）阶段任务暂停，变更生效后恢复。

  • 任务锁定判定：任务「已完成」（✓ 绿色前缀）或「进行中 / 待确认」（⏳ 黄色前缀，in_progress / confirming）时锁定。

  • 兜底校验：删除阶段需至少保留一个阶段（提示「至少保留一个阶段」）；删除任务 / 删除阶段均有二次确认弹窗（删除阶段提示其下任务将一并删除）。
  • 演示数据：原型进入变更页时若无任何已执行任务，自动为第二阶段注入「已完成 / 进行中」任务各一项，用于演示上述锁定交互。
提交校验与流转点击「提交变更」：变更原因必填（为空显示行内错误并聚焦）→ 校验通过后提案落库（写入 changeProposal 并追加「发起变更」变更记录）→ 轻提示「变更申请已发起，等待对方确认」→ 约 0.7s 后返回详情页 changing（变更中，见 9.5.1），阶段任务暂停流转。
关键逻辑与交互细节
  • 去平台审核：与合规版最大差异——提交变更后无需平台审核，直接进入双方确认环节。
  • 金额对比高亮：变更金额差异行实时联动（+绿 / −红），便于双方快速识别差异；变更摘要卡片亦以「旧值 → 新值」高亮。
  • 阶段任务暂停：提交变更瞬间，阶段任务即暂停流转（changing / change_confirming / change_confirming_sender 期间均暂停），变更生效后恢复。
  • 生成 V2 版本：受邀方确认变更后合同即升级为 V2（无上传签约文件环节），原 V1 保留于「版本与流转」记录可回溯（见 9.6）。
  • 取消不落库：点击「取消」直接返回详情页已签约态，本地编辑内容不落库、状态不变。

10.3.3 动态生成规则（工人合同）

工人合同状态由 确认中(worker_inviting) 流转至 已签约(worker_signed)（乙方首位确认者确认成功即签约完成，见 §7.5.3.4 / §8.4）时，系统自动向「项目动态」生成一条动态记录，文案与字段模型与非工人合同一致（见 §6.3.4）。规则如下：

  • 生成时机：状态由 worker_inviting 流转至 worker_signed（受邀方首位确认者确认成功，签约完成）时生成，时间 = 签约完成时间；归入「项目动态」（activity-list）对应日期分组（当天归入「今天（dateLabel）」）。
  • 动态文案：固定为「{合同名称}签约完成」（{合同名称}=本合同名称）。
  • 动态记录字段：同 §6.3.4 合同类动态数据模型——操作人（user）= 系统（由受邀方确认动作触发生成）；类型（type）= 合同类动态（contract）；类型标签（typeLabel）=「合同签约」；来源（source）= 所属项目 / 合同名称；媒体文件（files）默认空集合；是否有权限查看（hasPermission）按项目成员权限判定。
签约动态补充说明

① 动态记录与签约动作一一对应，供项目成员在「项目动态」中按类型 / 日期筛选查看；动态为系统自动生成，不向用户暴露填写入口。
② 工人合同动态对已在项目内的成员（含已确认加入架构层级的乙方工人）可见。
③ 与 PC 端「操作记录」时间线节点（见 §2.6 / §2.7）同源互补，由同一签约动作触发。

11.4 只读展示与放大查看
  • 展示形态：3 列网格、方形缩略图，每张可带标题。
  • 空数据规则：只读场景下某组无图片时，该组整块不展示（含「工艺参考示例」标题与「暂无工艺参考示例」占位文案）；两组均无图片时任务详情不出现任何相关区块。
  • 配置场景例外：可编辑的配置区在无图片时仍保留配置区与空态提示，便于上传。
  • 点击放大：点击缩略图在当前页面（手机框 / PC 弹窗）上层打开浮层查看大图，点击浮层任意处或关闭按钮收起；不发生页面跳转、不改变任务状态。

11.5 展示位置与排序规则
