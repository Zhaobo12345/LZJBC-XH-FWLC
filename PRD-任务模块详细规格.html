1.1 状态定义
状态值 状态名称 进入条件 可执行操作
configuring 待配置 合同创建任务后默认状态 配置执行人、配置确认人、提交任务
pending 待开始 配置完成并提交后 开始执行（执行人）、查看详情
in_progress 执行中 执行人点击"开始执行" 上传执行记录、提交验收
confirming 确认中 执行人提交验收后 确认通过、驳回（确认人）
completed 已完成 所有确认人确认通过后；或任务未配置确认人时，执行人提交执行记录后（快捷完成，跳过「确认中」） 查看详情、评价（业主）
1.2 确认结果与主状态映射

「确认中」为多人确认阶段，确认人对单条确认记录给出确认结果（confirmed / rejected）；该结果不是任务主状态，而是驱动任务主状态流转的依据：

确认结果触发条件任务主状态变化记录处理
已确认（confirmed）所有确认人均确认通过确认中 → 已完成各确认人确认记录（结果=已确认）留存
已驳回（rejected）任一确认人点击"驳回"确认中 → 待开始（状态回退，非新增独立主状态）该确认人的驳回记录（结果=已驳回、驳回原因）留存；任务在「待开始」选项卡 以"已驳回·需重新执行"标识呈现

说明：「已驳回」是「确认中」状态的一种确认结果，而非任务主状态。被驳回后任务主状态回退为「待开始」，由执行人重新执行，重新执行后再次进入「执行中 → 确认中」；确认记录始终留存，便于追溯。

1.3 无确认人快捷完成（状态流转场景）

确认人为选填角色。当任务未配置任何确认人（确认人列表为空）时，确认环节无对象参与，系统自动跳过「确认中」阶段，建立一条「执行中 → 已完成」的快捷流转分支：

触发条件状态流转可执行 / 跳过操作记录生成
任务处于「执行中」，且确认人列表为空，执行人提交执行记录 执行中 → 已完成（直接流转，跳过「确认中」） 无「确认通过 / 驳回」操作（无可确认人）；执行人提交执行记录即视为验收通过 不生成确认记录；执行记录（附件 / 说明）留存为该任务完成依据
无确认人快捷流转与主状态机关系

「无确认人」并非新增主状态，而是主状态机在「执行中」之后的一条条件分支：当确认人列表为空时，「执行中」不经「确认中」节点直接抵达「已完成」；只要配置了至少一位确认人，仍走「执行中 → 确认中 → 已完成」标准流程。该场景不影响其他状态的进入条件与操作。

驳回流程说明

「已驳回」不是任务的主状态，而是「确认中」阶段的一种确认结果。任务在「确认中」被任一确认人驳回后，其主状态回退为「待开始」（状态回退效果），并在「待开始」选项卡 中额外显示"已驳回·需重新执行"标识；确认记录（结果=已驳回、驳回原因）始终留存。执行人重新执行后任务再次进入「执行中 → 确认中」流程。

2.4 列表卡片规格（合同 / 阶段 / 任务）

列表页采用「合同 → 阶段 → 任务」三级分组结构（详见 §2.2 页面结构）。以下按三级逐一定义卡片字段与展示规则；交互（展开/收起、跳转）统一在 §2.4.4 描述。

⚠️ 任务列表数据范围（全部任务来源 · 重要）

任务列表（服务方 §2.4 / 业主方 §5.5）所展示的全部任务，其数据来源统一限定为：「已签约的合同」内的「全部有效任务」。

  • 已签约：仅合同状态为 signed / worker_signed（含变更生效后 V2 版本）时，其下任务才纳入任务列表；处于「已确认」及之前态、或处于变更锁定中的合同，其任务不进入任务列表（与 合同模块 §3.10.14「签约前锁定」 一致）。
  • 有效（= 未被删除）：仅展示逻辑上未被删除的任务；被删除（软删除）的任务不出现在列表中。

2.7 任务状态详解（服务方全部任务列表）
以下按任务在列表中的实际状态逐一说明

状态流转

通过后的状态流转：任务主状态由「确认中」流转为「已完成」；若该任务此前曾被驳回页面效果为「已完成（含驳回）」。多确认人场景下需全部确认人确认通过才完成流转，期间展示确认进度（如"确认进度：1/3"）。确认成功 轻提示 中部显示"确认成功"，持续 2 秒。

驳回后的状态流转：任务主状态由「确认中」回退为「待开始」，呈现为「驳回后待开始（REJECTED_PENDING）」；若该任务为「确认中（被驳回后）」再次被驳回，仍回退至「待开始」由执行人重新执行。任务在「待开始」列表以"已驳回·需重新执行"标识呈现。

多确认人确认与驳回（状态流转细化）

第一人确认后其他确认人的效果：多确认人场景下，第一位确认人确认通过后，任务主状态仍保持「确认中」，不发生完成流转；其余确认人保持"待确认"状态，继续等待逐一确认。确认进度实时更新（如"确认进度：1/3" → "2/3" → "全部确认人已确认"），步骤条进度同步推进（"x/3 已确认"）。每位确认人在本轮内仅可确认 / 驳回一次，已确认的确认人不再出现在"待确认"队列；只有全部确认人确认通过，任务才流转为「已完成」（此前曾被驳回则呈现「已完成（含驳回）」）。

任一确认人驳回后，此前已确认人仍需重新确认（需求）：多确认人场景下，任一确认人发起驳回，任务即回退为「驳回后待开始（REJECTED_PENDING）」，由执行人重新执行。此时不论其他确认人此前是否已确认，"所有"确认人的确认状态均被重置为"待确认"，需在执行人重新提交执行记录、任务再次进入「确认中」后，逐一重新确认——即此前已确认的确认人不能豁免，必须再次确认方计入新一轮进度。被驳回轮次产生的各确认人确认记录标记为"已驳回"并留存（含驳回原因），不计入新一轮确认进度。

相关记录生成与动态生成

相关记录生成：确认通过后生成一条确认记录（确认人、确认时间、附件、评语、综合评星、评价标签），状态记为"已确认"；驳回后生成一条驳回记录（确认人、驳回时间、附件、驳回原因），状态记为"已驳回"并留存驳回原因，原确认/执行相关记录保留为历史。

动态生成：① 确认进度随各确认人确认实时动态更新；② 全部确认后自动生成「已完成」状态与汇总记录，并通知执行人/业主；③ 驳回后任务在「待开始」列表动态呈现"已驳回·需重新执行"标识，并自动通知执行人重新执行；④ 原确认记录在详情页动态标记为"已驳回"，与驳回原因一并留存展示。

任务详情页在原型中实际渲染出 9 个状态视图，对应枚举如下。其中「驳回后待开始」「确认中（被驳回后）」「已完成（含驳回）」是「确认中」阶段的衍生结果态，不属于 §一 主状态机中的独立主状态（主状态机仅 待配置 / 待开始 / 执行中 / 确认中 / 已完成 5 个）；它们的出现是为了在详情页精确呈现「已驳回」这一确认结果带来的状态回退与历史留存。

原型渲染态枚举归属主状态说明
待配置configuring待配置任务已生成，尚未配置执行人与确认人
待开始pending待开始已配置执行人，等待执行人开始执行
待开始（前置阻塞）pending_blocked待开始设置了按序执行，前置任务未完成而被阻塞
执行中in_progress执行中执行人已上传记录，尚未提交确认
确认中confirming确认中执行人已提交，等待确认人确认
确认中（被驳回后）confirming_after_reject确认中被驳回后执行人重新提交，进入新一轮（第 N 轮）确认（确认结果=已驳回 的回退后再确认，轮次无上限）
已完成completed已完成全部确认人确认通过
已完成（含驳回）completed_with_reject已完成经历驳回后最终全部确认通过，历史含驳回记录
驳回后待开始rejected_pending待开始确认中有人驳回，主状态回退为待开始（状态回退效果，确认记录留存）

2. 三类用户视角

视角原型角色值典型身份在原型中的能力
配置人configurer合同甲乙方 / 合同创建者（服务方）配置执行人、增删确认人、修改执行人；驱动状态流转
执行人executor项目内人员（可配置选择，含业主）上传执行记录、提交确认 / 重新提交确认
确认人confirmer项目内人员（可配置选择）在确认中阶段执行「确认通过 / 驳回（填原因）」
执行人可包含业主（业主自办类任务）

执行人（executor）的可选范围为「项目内人员」，包含业主本人。当任务属于「业主自办类」（典型如「室内业主个人用具占用施工场地，需在规定时间内搬移」），由配置人将业主选定为执行人，业主即承担执行人角色，在服务方小程序与服务方执行人视角一致地履行上传执行记录、提交确认 / 完成任务等职责。此类场景下业主同时具备「执行人」与「项目相关方」双重身份，但其确认人资格仍取决于是否被配置为确认人（业主自办类任务通常无需他人确认，走「完成任务」流程直接闭环）。详见第六章 §6.3.1。

视角切换机制

原型顶部「角色切换器」提供配置人 / 执行人 / 确认人 三个视角按钮，可在不退出页面的情况下预览不同角色看到的页面（待配置态隐藏通用角色切换器、改显「配置视角」专用切换器）。服务方任务详情页不提供独立的「业主」视角；业主在任务中作为确认人或相关方查看者时的专属体验，由「第六章 任务详情页（业主）」专门说明，本节聚焦上述三类视角。

3. 页面通用区块（各状态共享骨架）

  • 头部状态卡（task-header-card）：任务名称、所属阶段路径、状态徽标（task-status）、确认进度提示（confirm-progress）。按状态套用配色类：默认（待配置/待开始/前置阻塞/驳回后待开始）、in-progress（执行中）、confirming（确认中/被驳回后）、completed（已完成/含驳回）。
  • 流程步骤条（4 步：待开始 → 执行中 → 确认中 → 已完成）：以 已完成（completed）/ 当前（current）/ 默认 三态高亮当前进度，并显示进度百分比（flowProgressBar）。
  • 人员区：执行人信息卡 + 确认人列表（含每人头像、姓名·角色、确认状态、确认时间）。
  • 三段标准卡片（standard-card）：执行标准（📝 可折叠）、确认标准（✅ 可折叠）、担责标准（⚠️ 可折叠）；以编号列表（standard-list / standard-item）呈现每条标准，数据来源于引用模板或合同编辑时定义（具体由模板内配置格式决定，非模板内任务由创建人添加结果决定），各状态只读展示；点击头部「收起」可折叠隐藏。
  • 执行记录卡：执行人上传的图片/视频/文字，及「第 N 次执行」历史（含已驳回标识）；每次被驳回后执行人重新上传，上传轮次（upload_round）递增（首次为 1，第 2 次、第 3 次……第 N 次，轮次无上限，最新一次为当前轮）。
  • 确认记录卡：各确认人的确认/驳回结果、评语、标签、评分、附件，按轮次分组（第 1 轮 / 第 2 轮 / … / 第 N 轮，轮次无上限；最新轮为当前轮（进行中）、其余历史轮次半透明（opacity 0.6）留存）；轮次机制详见 §3.16「逻辑」。
  • 前置任务阻塞卡：仅前置阻塞态显示。
  • 底部操作栏 / 固定上传栏：随视角与状态变化的操作按钮。
3.11 待配置

🔗 原型演示：待配置 · 配置人视角 ｜ 待配置 · 只读（其他用户视角）

逻辑

任务由合同阶段模板生成后进入此态。页面驱动数据为「是否已有执行人（hasExecutor）」与「确认人列表（currentConfirmers）」。确认进度提示为「请配置执行人（必填）和确认人（选填）」。流程条仅第 1 步「待开始」为当前（current），进度 0%。

权限与用户视角

注：待配置态下执行人与确认人均尚未配置，不存在独立的「执行人视角」「确认人视角」（原型中该态仅支持配置人与其他用户视角，其余角色均回退为配置人视角）。

视角可见/可操作
配置人显示执行人添加入口（无执行人时显「+ 添加执行人」占位；有执行人时显执行人卡）；可增删确认人（addConfirmerBtn 显示）；操作栏为空（由配置动作驱动）
其他用户视角只读；可查看执行人卡、确认人列表（只读）；提示「任务正在配置中，请等待配置完成」；无操作按钮

字段

头部状态徽标「待配置」；确认人列表以「配置中」模式渲染（每项常显删除按钮）；执行记录卡与确认记录卡均隐藏；前置阻塞卡隐藏。

交互

  • 配置人点击「添加执行人」→ 弹出执行人选择器（可选范围为项目内人员）；选定后写入执行人卡。
  • 配置人点击「添加确认人」→ 弹出确认人选择器（最多 5 人，可选范围为项目内人员）；可移除已选确认人。
  • 配置执行人自动流转至「待开始」状态。

搜索匹配规则：执行人 / 确认人选择器均提供搜索框，输入关键字后按 姓名（name）或角色（role）模糊匹配（不区分大小写、子串包含即命中）；无匹配结果时列表区显示「未找到匹配的成员」空态提示。可选人员范围始终为项目内人员。

效果

头部默认配色；流程条第 1 步高亮「⏸ 待开始」；确认进度区用红色标注执行人为必填、灰色标注确认人为选填。

3.12 待开始

🔗 原型演示：待开始 · 配置人视角 ｜ 待开始 · 执行人视角 ｜ 待开始 · 确认人视角 ｜ 待开始 · 其他用户视角（只读）

逻辑

执行人已配置，等待执行人开始执行。确认进度提示「等待执行人执行」。流程条第 1 步当前（current），进度 0%。执行记录卡与确认记录卡隐藏。

权限与用户视角

视角可见/可操作
配置人显执行人卡 + 「修改执行人」入口（可改派执行人）；可增删确认人（「+ 添加确认人」与删除按钮均显示）；操作栏为空（显示「等待执行人执行」）；固定上传栏隐藏。
执行人底部显「上传记录」「提交确认 / 完成任务」按钮（有确认人时文案「提交确认」，无确认人时「完成任务」）；固定上传栏显示；其余模块（人员区/三段标准/流程条）只读；未上传执行记录时「提交确认 / 完成任务」按钮置灰不可点击（提示「请先上传执行记录」），上传并流转「执行中」后方可点击提交。
确认人只读；操作栏「等待执行人执行」；固定上传栏隐藏，无上传/提交入口。
其他用户视角只读；可查看执行人卡、确认人列表（只读）；操作栏「等待执行人执行」；固定上传栏隐藏，无上传/提交入口。

字段

头部状态徽标「待开始」；人员区显示执行人卡与确认人列表（只读，无删除按钮）；执行记录卡 / 确认记录卡 / 前置阻塞卡隐藏。

交互

  • 执行人「上传记录」→ 打开上传弹窗（图片/视频/文字/音频）；确认上传后任务即由「待开始」流转至「执行中」，记录显示在「执行人上传的内容」区。
  • 上传记录在「提交确认 / 完成任务」之前支持多次操作：进入「执行中」后可继续上传、编辑或删除记录（删除至空则退回「待开始」）。
  • 执行中态下，执行人点击「提交确认」（有确认人时）流转至「确认中」；点击「完成任务」（无确认人时）直接流转至「已完成」（提交 / 完成动作详见 §3.14）。
  • 配置人「修改执行人」→ 重新打开执行人选择器。

上传记录（数据结构与提交交互）

执行人点击「上传记录」打开上传弹窗，可添加图片 / 视频 / 音频媒体文件（按类型调起系统文件选择，单次选取一个，可多次添加），并填写执行说明（文本，选填）。点击「确认上传」后生成一条执行记录并入库。

一条执行记录包含的字段规格：

字段类型 / 取值必填性校验规则说明
媒体文件（files）数组；每项含 name（文件名，字符串）、type（MIME 类型，字符串）、size（文件大小，数值）条件必填（与「执行说明」至少一项）① 与「执行说明」至少一项非空，否则提示「请至少上传一个文件或输入执行说明」；② 每项 type（MIME 类型）须为 image/*、video/*、audio/* 之一（原型按此限定文件选择）；③ name（文件名）、type（MIME 类型）、size（文件大小）三项均需存在；④ 单文件 size（文件大小）应不超过 20MB（与 §3.5 上传限制保持一致），超出应在选完即提示（文件过大）并丢弃。本次上传的媒体文件集合；size（文件大小）为文件原始字节数（取自文件对象的 size 属性）。页面以缩略图网格展示，图片 / 视频 / 音频分别以 📷 / 🎬 / 🎵 标识，视频缩略图附「0:15」时长占位。
执行说明（desc）字符串（文本）选填与「媒体文件」至少一项非空；纯文本，无长度限制。对本次执行内容的文字描述，留空不影响提交。
提交时间（time）字符串，格式「月-日 时:分」系统自动（无需用户填写）由系统按记录入库时刻自动生成。用于记录列表排序与展示（如「08-14 15:30」）。

执行记录区展示与操作项（首传后流转「执行中」可见）

首次上传确认后，任务由「待开始」自动流转至「执行中」，原在「待开始」态隐藏的执行记录卡（标题「📤 执行人上传的内容」）出现并逐条展示执行记录；每一条展示：序号「执行记录 #N」、提交时间、媒体缩略图网格、执行说明（有则显示）。

执行人视角的操作项（显示条件：当前视角 = 执行人，且任务主状态处于「待开始 / 执行中 / 待开始（前置阻塞）/ 驳回后待开始」之一，即尚未进入任何确认 / 完成态）：

操作项位置流程交互
上传记录 / 继续上传底部操作栏「上传记录」按钮；卡片标题右侧「✎ 上传」（尚无记录时）/「+ 继续上传」（已有记录时）打开上传弹窗，确认后新增一条执行记录。若该任务仍为「待开始」，则随首条记录入库自动流转至「执行中」；若已在「执行中」则仅追加记录、状态不变。
编辑（✎）每条记录右上角将原记录的文件与说明回填至上传弹窗；确认后就地更新该条记录（提示「执行记录已更新」），不改变任务状态。
删除（✕）每条记录右上角移除该条记录并刷新列表；若删除后记录列表为空且任务处于「执行中」，则自动退回「待开始」。

只读视角（配置人 / 确认人 / 其他用户 / 非执行人）仅展示记录内容，不显示上传 / 继续上传 / 编辑 / 删除任何操作项。逐条操作在「执行中」态持续可用，详见 §3.14。

效果

头部默认配色；流程条第 1 步「⏸ 待开始」当前（current）；底部主按钮为品牌主色（primary）；尚未上传执行记录时「提交确认 / 完成任务」主按钮置灰（disabled），待上传并进入「执行中」后恢复可点击。

提醒规则（执行人服务号通知 · 不生成应用内待办）

任务进入「待开始」后系统不生成应用内待办（「合同任务执行」待办类型已取消），执行人通过任务列表与任务详情页自行查看待开始任务。确认为执行人后由系统推送一条微信服务号通知（订阅消息，见 wechat-service-notice.html 原型），提示其查看待开始任务并开始执行；完整触发条件与变更作用域（仅变更项任务）以合同模块为权威出处：见 PRD-合同模块 §3.10.14 已签约 / §5.15.8 变更已生效。

3.13 待开始（前置阻塞）

🔗 原型演示：前置阻塞 · 执行人视角 ｜ 前置阻塞 · 确认人视角 ｜ 前置阻塞 · 配置人视角 ｜ 前置阻塞 · 其他用户视角

逻辑

任务设置了「按序执行」且前置任务未完成，进入阻塞。确认进度提示「等待前置任务完成」。显示前置任务阻塞卡（preTaskBlockCard）：列出前置任务名称、执行人、状态（如「进行中」）；卡片底部提示「完成后将自动通知执行人」。前置任务条目可点击，跳转至该前置任务的详情页（原型以执行中示例态演示跳转，真实环境携带该前置任务的 taskId 参数）。流程条第 1 步当前（current），进度 0%。

权限与用户视角

视角可见/可操作
配置人显执行人卡 + 「修改执行人」入口（可改派，阻塞态改派不改变阻塞状态）；可增删确认人；操作栏「等待执行人执行」（只读性质）
执行人底部显禁用态按钮「🔒 前置任务未完成」（opacity 0.6、不可点击）；固定上传栏仍显示但无提交入口
确认人只读等待

字段

头部状态徽标仍为「待开始」（与待开始同主状态）；前置阻塞卡显示；执行记录卡 / 确认记录卡隐藏。

交互

  • 配置人「修改执行人」→ 弹出执行人选择器（搜索匹配项目内人员，按姓名 / 角色模糊匹配），选定后更新执行人卡（改派新执行人）并通知新执行人；任务仍保持「待开始（前置阻塞）」，阻塞不解除（阻塞由前置任务决定，与执行人是谁无关）。
  • 前置任务完成后由系统自动解除阻塞，状态回到「待开始（可执行）」。

效果

前置阻塞卡以锁形图标（🔒）+ 提示文案突出「阻塞」语义；执行人操作按钮置灰禁用，明确不可越序执行；执行人视角无「提交确认 / 完成任务」入口（为禁用态「🔒 前置任务未完成」按钮），故「未上传前不可提交」约束在前置阻塞态天然满足。

3.14 执行中

🔗 原型演示：执行中 · 执行人视角 ｜ 执行中 · 确认人视角 ｜ 执行中 · 配置人视角 ｜ 执行中 · 其他用户视角

逻辑

执行人已上传至少一条记录但尚未提交确认。头部套用 in-progress 配色，状态徽标「执行中」，确认进度「执行人正在执行任务」。流程条第 1 步已完成（completed）、第 2 步当前（current），进度 25%。执行记录卡显示，确认记录卡隐藏。

权限与用户视角

视角可见/可操作
配置人可增删确认人；操作栏「执行人正在执行中...」
执行人执行记录卡显「✎ 上传」编辑入口；底部「上传记录」「提交确认 / 完成任务」；固定上传栏显示；可继续补充记录
确认人只读；操作栏「执行人正在执行中...」；确认记录卡隐藏（尚未进入确认）

字段

执行记录卡显示「执行人上传的内容」（当前轮），含图片网格、文字说明、提交人/时间、绿色「任务已完成」提示块；历史记录区隐藏；确认人列表只读（删除按钮隐藏）。

交互

执行人底部主按钮文案随「是否配置确认人」动态切换：已配置确认人显「提交确认」；无确认人显「完成任务」。两者共用同一提交确认弹窗，弹窗内容按有无确认人切换呈现。提交前置条件：须至少已上传一条执行记录（否则按钮置灰不可点击，详见 §3.12「提交前置校验」）。

（1）执行人点击「提交确认」（有确认人时）

  • 触发弹窗：点击底部「提交确认」→ 弹出「提交确认」弹窗（标题「提交确认」，顶部 📤 图标）。
  • 弹窗提示内容：① 主文案「确定要提交确认吗？」；② 警示文案「⚠️ 提交后不支持修改执行记录」（始终显示，提示提交后执行记录将变为只读）；③ 确认人列表区展示「确认人列表：」及全部已配置确认人（项目内人员，含姓名 / 角色）。
  • 弹窗按钮项：①「取消」（次要按钮）→ 关闭弹窗，不做任何状态变更；②「确认提交」（主要按钮）→ 执行提交。
  • 点击「确认提交」后续：弹窗关闭 → 轻提示「已提交确认，请等待确认」（约 2.5 秒自动消失）→ 任务状态流转至「确认中（confirming）」→ 系统通知确认人（后续由确认人执行 §3.15 的确认 / 驳回）；同时按下方「提交后记录生成规则」生成一条「提交动作」执行记录与一条动态记录（时间 = 提交确认时间）。

（2）执行人点击「完成任务」（无确认人时）

  • 触发弹窗：点击底部「完成任务」→ 弹出「完成任务」弹窗（标题「完成任务」，顶部 📤 图标）。
  • 弹窗提示内容：① 主文案「确定要完成任务吗？」；② 警示文案「⚠️ 提交后不支持修改执行记录」（始终显示）；③ 确认人列表区隐藏（无确认人，无需展示）。
  • 弹窗按钮项：①「取消」（次要按钮）→ 关闭弹窗，不做任何状态变更；②「确认完成」（主要按钮）→ 执行完成。
  • 点击「确认完成」后续：弹窗关闭 → 轻提示「任务已完成」→ 任务状态直接流转至「已完成（completed）」（无确认人环节，不进入确认中）；同时按下方「提交后记录生成规则」生成一条「提交动作」执行记录与一条动态记录（时间 = 提交确认时间）。

提交后记录生成规则

执行人点击「确认提交」（提交确认）或「确认完成」（完成任务）后，系统除流转任务状态外，还会生成一条「提交动作」执行记录与一条动态记录。两条记录均由同一提交动作触发、以「提交确认时间」为时间锚点，规则如下（两种提交路径一致，仅动态类型标签不同）。

（3）执行记录生成规则（提交动作记录）

  • 生成时机：与状态流转同时，于执行人点击「确认提交」/「确认完成」后由系统生成，时间 = 提交确认时间。
  • 记录内容：系统生成一条「提交动作」执行记录（记录本次提交行为本身，含提交动作、提交人、提交时间、来源任务），不对既有上传记录做汇总 / 合并。执行中（in-progress）阶段由执行人逐条上传的执行记录（上传的媒体文件与执行说明）保持原样、各自独立存在，不被封装为单条快照。
  • 关键字段：提交动作（提交确认 / 完成任务）、提交人（执行人）、提交时间（提交确认时间）、来源任务。
  • 说明：该记录仅标识「执行人已提交」这一动作节点；既有逐条上传记录继续保留，可被确认人逐一查看，且状态提交后全部转为只读（不可再编辑 / 删除）。

（4）动态记录生成规则（项目动态）

  • 生成时机：与「提交动作」执行记录同时生成，时间 = 提交确认时间，归入「项目动态」（activity-list）对应日期分组（提交当天归入「今天（dateLabel）」）。
  • 聚合规则：动态仅对执行记录中的媒体文件做汇总——将本次提交全部执行记录的媒体文件合并为一条媒体集合（是否有媒体（hasMedia）/ 媒体数量（mediaCount）据此取合并值）；文字描述不逐条汇总，统一为本次操作的标准动态文案：有确认人时执行人「完成了{阶段名称}{任务名称}的施工」（任务提交）、无确认人时执行人「{阶段名称}{任务名称} 已完成」（任务完成）（{阶段名称}=所属阶段名称（来源），{任务名称}=当前任务名），不再生成「提交 N 条、含 M 个媒体」之类的逐条汇总描述。

（5）待办生成规则（确认人「任务确认」待办）

  • 生成时机：执行人点击「确认提交」（提交确认，有确认人时）使任务流转至「确认中（confirming）」后，系统为每一位已配置的确认人自动生成一条「任务确认」待办；生成时间 = 提交确认时间。点击「确认完成」（完成任务，无确认人时）不生成确认待办（无确认人可生成）。
  • 待办类型与归属：对应 §4.3「合同任务确认」待办类型（标签「任务」，状态值 confirming，数据来源「任务状态为确认中且当前用户为确认人」）；待办仅对「当前用户为该任务确认人」的成员可见，每位确认人各得一条、互不重复。
  • 跳转目标：点击待办卡片跳转 task-detail.html?status=confirming&role=confirmer，进入本人确认视角直接执行 §3.15 确认 / 驳回。
  • 状态联动：确认人完成本人确认后，其对应的「任务确认」待办自动标记 completed（从「待处理」移至「已处理」）；若任务被驳回回退「驳回后待开始」，原 confirming 来源的待办随状态变更不再匹配而移出待处理，待执行人「重新提交确认」后再次进入确认中时由本规则重新生成。
  • 说明：待办由系统自动生成，本规则仅新增「执行人提交确认 → 确认人确认待办」这一待办来源，不改变 §4.3 其他既有待办类型及功能描述。

执行人「上传记录 / ✎ 上传」→ 继续追加执行记录（轮次递增），详见下方执行记录区说明。

提交后执行记录进入只读（不可再编辑 / 删除），由弹窗警示文案体现；执行人视角在「确认中 / 已完成」等后续状态不再提供提交入口，详见 §3.15、§3.18。执行记录区的逐条操作项（上传记录 / 继续上传 / 编辑 / 删除）的字段结构、展示形式与完整流程交互，详见 §3.12「上传记录（数据结构与提交交互）」「执行记录区展示与操作项」。

效果

头部执行中（in-progress）配色；流程条进度 25%；执行记录区绿色提示块强化「已提交结果，待确认」氛围。

确认 / 驳回后记录生成规则

每位确认人点击「确认通过」或「确认驳回」提交后，系统除流转任务状态（进度 +1 / 回退待开始 / 全部完成）外，还会生成一条确认记录与一条动态记录。两条记录均由同一确认动作触发、以「该确认人确认时间」为时间锚点，规则如下（确认与驳回两种动作一致，仅确认结果 / 动态类型标签不同）。

（3）确认记录生成规则（确认 / 驳回结果记录）

  • 记录内容：系统生成一条「确认结果」记录（对应 §8.3 确认记录表字段（task_confirmations）一行），记录本次确认人给出的确认结果本身（含任务、确认人、确认结果、确认备注、确认时间、所属轮次、媒体附件等），确认中（confirming）阶段由多位确认人逐条给出的确认结果保持原样、各自独立存在，相互不合并。
  • 关键字段：任务（来源任务）、确认人（confirmer_id）、确认结果（status）：已确认（confirmed）/ 已驳回（rejected）、确认备注（remark，选填）、确认时间（confirmed_at，系统填充）、所属轮次（如 第 1 轮 / 第 2 轮）、媒体附件（files，确认人上传的媒体附件，选填）。上述核心字段对应 §8.3「确认记录表字段（task_confirmations）」，确认弹窗的评语 / 综合评星 / 评价标签与驳回弹窗的驳回原因随确认备注（remark）及附件一并留存。
  • 说明：该记录仅标识「某确认人已给出确认结果」这一动作节点；确认记录始终留存（含被驳回项），便于追溯各轮次确认 / 驳回全过程，不因任务主状态回退或最终完成而清除。

  • 生成时机：与「确认结果」记录同时生成，时间 = 该确认人确认时间，归入「项目动态」（activity-list）对应日期分组（确认当天归入「今天（dateLabel）」）。
  • 动态文案细分：① 单条确认（非全部完成）：「{确认人姓名} 确认了 {阶段名称}{任务名称}」（类型标签（typeLabel）=「任务确认」）；② 驳回：「{确认人姓名} 驳回了 {阶段名称}{任务名称}」（类型标签（typeLabel）=「任务驳回」）；③ 最后一人确认（全部确认）→ 任务已完成：「{阶段名称}{任务名称} 已完成」（类型标签（typeLabel）=「任务完成」，与 §3.14 完成任务动态完全一致，但此处由确认流程驱动）。

🔗 原型演示：确认中（被驳回后） · 确认人视角 ｜ 确认中（被驳回后） · 只读（非确认人视角）

历史记录区半透明 + 灰底，突出「历史」；第 1 轮被驳回归项红底「驳回原因」块，强化「为何重做」的上下文；确认记录卡以「第 1 轮 / 第 2 轮 / … / 第 N 轮（轮次无上限）」分组清晰区分当前确认与历史，第 1 轮被驳回归项以半透明留存；流程条与确认中相同（第 3 步当前（current），50%）。

业主作为执行人场景（§6.3.1）

场景概述

部分任务需由业主自行完成而非交由服务方执行，典型如「室内业主个人用具占用施工场地，需在规定时间内进行搬移」。此类「业主自办类任务」由配置人（服务方 · 工长）在配置阶段将业主本人选定为执行人，业主即承担「执行人」角色，在服务方小程序与服务方执行人视角一致地履行执行职责。业主在自办类任务中同时具备「执行人」与「项目相关方」双重身份；因其为任务执行方，通常不再单独配置确认人，走「完成任务」流程由系统直接闭环（亦可按需在确认人列表中加入服务方人员做验收）。

执行人 = 业主时（业主自办类任务）

当本任务将业主配置为执行人时，业主在本态具备与服务方执行人视角一致的真实重新执行能力（权限与配置方式见 §6.3.1），逻辑、字段、效果对齐 §3.17 驳回后待开始（执行人视角），要点如下（细则复用 §3.17，不再展开）：

四、担责标准该任务配置的担责标准条目文本列表。
五、执行情况执行结果（合格 / 不合格）、施工内容、执行人提交的现场照片（图片 + 视频）汇总自执行记录卡。
六、确认记录表格：确认人 / 角色 / 确认结果（合格）/ 确认时间汇总自确认记录卡，按确认轮次列出全部确认人。
七、确认人评价及附件各确认人：姓名 / 角色 / 评星（未评价占位）/ 评语 / 附件（图片 / 视频）/ 评价时间汇总自确认记录卡中的评价字段，与 §3.16「评价表单字段规格」一致。
底部说明报告生成时间系统填充。

📌 无确认人场景的结构差异：当任务未配置确认人时（见 §10.4「生成时机 · 无确认人」），报告单仅含「一、基本信息」至「五、执行情况」五个区块 + 底部说明，不展示「六、确认记录」与「七、确认人评价及附件」两个区块（无确认环节、无确认人评价可呈现）。原型示例见 service-miniapp/task-report-no-confirmer.html。

10.3 操作栏与交互
操作说明
下载报告底部主按钮；点击将报告单保存至手机本地（详见下方「下载报告 · 手机端本地保存交互」）。
返回导航栏「← 返回」或系统返回，回到来源任务详情页。

下载报告 · 手机端本地保存交互

微信小程序无直接访问手机文件系统的能力，「下载报告」本质是将报告单渲染为图片 / 文件后保存至手机本地（相册或小程序文件目录），具体流程：

  • ① 触发渲染：点击「下载报告」→ 系统将当前报告单（纸质单据）渲染为一张长图（或 PDF 文件），同步弹出轻提示「报告生成中…」（约 1.5 秒，原型以 toast 模拟）。
  • ② 调用微信保存能力：
    • 图片形式（默认）：渲染为长图后调用 wx.saveImageToPhotosAlbum，请求写入手机相册；首次触发微信原生授权弹窗「是否允许保存到相册」。
    • 文件形式（可选）：渲染为 PDF 后调用 wx.downloadFile 落至小程序私有目录，再以 wx.openDocument 打开预览，用户可经「用其他应用打开 / 转发」导出至本地文件管理。
  • ③ 授权结果处理：
    • 用户「允许」→ 保存成功，轻提示「已保存至相册」（原型以「报告已下载」toast 模拟）；用户可在系统「相册 / 文件管理」中查看该报告图。
    • 用户「拒绝」或系统拦截 → 轻提示「保存失败，请在微信设置中开启相册权限」，不重试、不阻断页面。
  • ④ 与「分享报告」边界：本版仅提供本地保存，「下载报告」不包含转发给微信好友 / 微信群等分享能力（分享功能已取消，见 §10.3 操作栏仅「下载报告」一项）。

原型说明：service-miniapp/task-report.html / owner-miniapp/task-report.html 的「下载报告」以 downloadReport() 模拟——点击后依次 toast「报告下载中…」「报告已下载」，不实际调用微信保存 API，仅演示交互时序。

进入方式：任务详情页「已完成」/「已完成（含驳回）」状态，操作栏「查看报告单」（次要按钮，onclick="goToTaskReport()"）跳转至 task-report.html?taskId=…；「查看评价」（主按钮）保持打开评价列表弹窗。两按钮并列展示。

10.4 生成规则

任务报告单为任务最终结果态的聚合单据，由系统在任务达到「已完成」终态时自动生成，详情页「查看报告单」仅读取、不重新生成。

规则项说明
生成时机任务状态流转至「已完成（completed）」或「已完成（含驳回）（completed_with_reject）」终态时，由系统自动生成一份报告单。覆盖两类场景：
  • 有确认人：即最后一位确认人确认通过、全部确认人确认完毕时生成（见 §3.14「提交确认」→ §3.15 确认流转）。
  • 无确认人：执行人点击「完成任务」（无确认人时，见 §3.14(2)「完成任务」）使任务直接流转至「已完成（completed）」，不进入确认环节，系统于执行人完成提交的同时即时生成报告单。该场景报告单仅含「一~五」五个区块（基本信息 / 执行标准 / 确认标准 / 担责标准 / 执行情况）+ 底部说明，不展示「六、确认记录」「七、确认人评价及附件」两个区块（原型示例见 task-report-no-confirmer.html）。
仅「已完成」终态生成；处于「确认中 / 驳回后待开始」等中间态时报告单尚不存在，「查看报告单」入口不出（对应任务详情页操作栏不展示该按钮，见 §3.16 / §3.19 / §6.9 / §6.12）。
生成主体系统自动生成，不依赖人工手动「生成报告」操作；服务方与业主方任务同源，各方任务详情页的「查看报告单」读取同一份报告。
报告编号由系统按规则生成，形如 HT-2024-001-001：前段取自所属合同编号（HT- + 合同年份 + 合同序号），末段「-001」为该合同下任务序号（同一合同第 N 个任务递增）；原型以演示值 HT-2024-001-001 呈现。
生成日期 / 报告生成时间取任务终态达成时间：有确认人时 = 最后一位确认人确认时间；无确认人时 = 执行人点击「完成任务」的完成提交时间。该时间系统填充于编号下方与底部说明。
内容聚合来源报告七区块字段（有确认人场景；无确认人场景仅含「一~五」区块，不含确认记录与确认人评价，见 §10.4 生成时机）实时聚合自任务及其所属阶段、执行记录卡、确认记录卡、确认人评价字段：基本信息 / 执行标准 / 确认标准 / 担责标准取自任务与阶段配置；执行情况取自执行记录卡（结果、施工内容、现场照片）；确认记录取自确认记录卡（确认人 / 角色 / 结果 / 时间）；确认人评价及附件取自确认记录卡中的评价字段（评星、评语、附件、评价时间），字段规格同 §3.16「评价表单字段规格」。
「已通过」戳章条件仅当任务最终为「全部确认通过」终态（无驳回留痕或驳回已全部重新确认通过）时展示标题区「已通过」戳章；含被驳回且已完成轮次的历史记录仅作为报告内「确认记录 / 评价」留存，不影响戳章展示。
持久化与读取报告单随任务终态生成后落库留存，任一相关方再次「查看报告单」均读取同一份快照；任务终态数据发生变更（如评价补录）时以生成时快照为准，不强制刷新。
