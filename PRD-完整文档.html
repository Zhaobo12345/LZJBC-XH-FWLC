二、产品概述

产品背景

随着家装行业的不断发展，传统的项目管理方式已无法满足现代家装项目的复杂需求。良造家管理平台旨在通过数字化手段，为家装项目提供一站式管理解决方案，实现项目全生命周期的可视化、规范化管理。

产品定位

良造家管理平台是一个面向家装行业的数字化管理工具，涵盖PC管理端和小程序端，为平台运营人员、服务方（设计师、施工团队、监理人员等）和业主提供全方位的项目管理功能。

产品价值

  • 提升效率：通过数字化流程，减少人工操作，提高项目管理效率
  • 规范管理：标准化合同流程和任务管理，确保项目质量
  • 信息透明：实时同步项目进度，确保各方信息对称
  • 便捷协作：支持多方协作，简化沟通流程
  • 角色清晰：明确区分不同角色的职能和权限，避免操作混乱

三、关键交互流程

PC端合同审核流程

1. 运营人员登录后进入合同列表页

2. 点击合同名称或"去审核"按钮进入合同详情页

3. 查看合同基本信息、合同正文、阶段任务、附件

4. 点击"审核通过"或"驳回"按钮

5. 驳回时需填写驳回原因

6. 审核后返回列表页，合同状态更新

服务方任务执行流程

1. 服务方用户进入任务列表页，查看待执行任务

2. 点击任务卡片进入任务详情页

3. 查看执行标准、确认标准、担责标准

4. 点击"上传记录"上传执行过程照片/视频

5. 执行完成后点击"提交验收"

6. 等待确认人确认验收

业主任务确认流程

1. 业主用户进入首页，查看待确认事项

2. 点击待确认任务进入任务详情页

3. 查看执行人信息、执行记录（照片/视频）

4. 确认合格：点击"确认验收"，可选填评价

5. 不合格：点击"驳回"，填写驳回原因

6. 驳回后任务返回执行中状态，需重新执行

对账单确认流程

服务方提交：

1. 服务方进入对账单列表页，点击新增按钮

2. 选择关联合同（自动带出确认人）

3. 选择账单类型、输入金额、填写用途描述

4. 提交后通知业主确认

业主确认：

1. 业主进入对账单列表页，查看待确认对账单

2. 点击卡片进入详情页

3. 确认无误：点击"确认无误"

4. 有问题：点击"驳回"，填写驳回原因

5. 确认后状态变为"已生效"，等待服务方上传支付凭证

七、消息功能

消息是平台内跨功能模块的独立能力，承载系统通知与各类业务提醒（加入项目邀请、工人合同邀约、系统公告等），可联动全部其他功能项。其中"任务指派 / 确认 / 驳回"等任务类提醒不再以消息 Tab 呈现，统一归口「待办」（详见《PRD-任务模块详细规格》）；消息页的布局、列表项与字段规格仅在本节描述（其他模块文档不重复），相关跨模块规则以引用为主以减少冗余。

7.1 页面定位与范围

消息页是服务方 / 业主小程序的统一消息中心，负责聚合来自各功能模块的业务消息并承载接收侧交互。其范围边界：

  • 覆盖范围：加入项目类邀请（两端）、工人合同邀约（仅服务方）。
  • 不覆盖范围：任务类提醒（归口「待办」）；合同正文编辑 / 变更流程本身（归口《PRD-合同模块详细规格》）；邀请的发起方式与权限（归口《PRD-项目模块详细规格》7.5 / 7.6，本节仅描述接收侧）。
  • 布局专有：消息页布局、列表项结构、卡片字段规格属消息页专有，仅在本节展开，其他文档不重复。
  • 站外触达：用户离开小程序时，平台通过微信「服务通知（订阅消息）」推送提醒并直达小程序内对应页面，归口 7.10，不属于消息页本身。
7.2 消息页面布局

消息页采用标准小程序页面骨架（自顶向下）：

区域 / 组件说明
状态栏 + 导航栏导航栏标题固定为"消息"；右侧为微信原生胶囊（⋯ ○），由微信客户端渲染、开发者不可自定义其内容（仅占位展示）。
消息分类 Tab 栏位于导航栏下方，横向排列各消息分类（见 7.3）；当前 Tab 高亮，点击切换并重新渲染列表；支持 URL 参数 ?tab= 直接定位（服务方）。仅当消息分类多于一个时展示：业主端仅含"邀请"一类，不展示分类 Tab 栏，消息直接列表渲染，未处理数量改由底部导航"消息"项角标呈现（见 7.5.3）。
消息列表中部可滚动区域，消息按日期（date）分组展示（分组标签如"今天 / 昨天 / 2024-01-15"），组内纵向排列消息卡片（Card）。

弹窗（Modal）与轻提示（Toast）覆盖于内容之上的通用层：确认弹窗（接受 / 拒绝邀请）、提示弹窗、选择加入角色弹窗；Toast 用于操作反馈（约 2s 自动消失）。
原型导航 / 演示面板仅原型页附加：侧边"原型导航"列出同端页面；"接受邀请演示控制"面板支持切换接收人已认证角色数（单 / 多角色）与扫码 / 微信邀请演示入口，属演示辅助、不计入产品范围。

7.5.3 未读角标规则

  • 服务方 邀请 Tab 角标：未读（unread=true）的邀请消息计数；为 0 时隐藏。
  • 合同邀约 Tab 角标：未读且状态为待处理（pending）的合同邀约计数；为 0 时隐藏。
  • 业主端 底部导航"消息"角标：因业主端仅"邀请"一类、不展示分类 Tab 栏，未读（未处理）邀请消息计数直接展示于底部 TabBar"消息"项右上角（红色圆角角标）；为 0 时隐藏。该角标随"全部已读"或单条已读实时更新（updateBadge 统一维护）。
7.6 交互逻辑与效果
  • Tab 切换：switchTab(tab) 切换 active 并重渲染本分类列表；服务方演示面板仅"邀请"Tab 展示。
  • 邀请接受 / 拒绝：点击"接受邀请"/"拒绝"→ 弹出确认弹窗（文案含项目名）→ 确认后消息状态更新、清除未读、刷新角标、重渲染；接受按 7.7 角色分支进入项目，拒绝轻提示"已拒绝邀请"。
  • 角色分支选择：多角色弹"选择加入角色"弹窗；"取消"则停留列表、消息仍为"已接受"、可再次进入项目。
  • 已接受进入项目：点项目卡或角色选择后调用 goToProject(projectName) 跳转项目详情页（轻提示"正在进入…"后约 0.6s 跳转）。
  • 合同邀约查看：点"查看邀约"→ 跳转 worker-contract-detail.html?viewer=receiver（接收方视角，实际带 asUserId 参数），查看并响应工人合同邀约。
  • 空状态：列表为空显示"暂无消息"图标与文案。
  • 轻提示（Toast）：操作反馈（如"已加入…正在进入…""已全部标记为已读"）约 2s 自动消失。
  • 外部跳转定位：支持 URL 参数 ?tab=contract 直接进入对应 Tab（服务方）。
  • 演示控制（仅原型）：单 / 多角色切换、扫码 / 微信好友邀请接收演示入口，便于演示角色分支差异。
7.7 邀请接收与角色确认规则（type=invite）

消息中心收到的"加入项目"类邀请（type=invite），无论其发起方式为平台内选择 / 二维码 / 微信好友，被邀请人点击"接受邀请"后的处理统一遵循本规则（两端"邀请" Tab 共用）。本规则是"邀请链路"在接收侧的闭环，与《PRD-项目模块详细规格》7.5（邀请方式）、7.6（邀请身份区分与默认权限）同源。

步骤行为说明
1. 触发确认点击消息卡片"接受邀请"弹出确认弹窗"确认接受邀请"（文案含项目名称）；"拒绝"则置为已拒绝，流程结束。
2. 状态更新确认接受消息状态置为"已接受"，卡片更新为可点击进入项目（与 7.7 落地端一致）。
3. 角色判断读取被邀请人已认证角色数 currentUser.verifiedRoles依据 users.certified_role_count / 已认证角色列表判断分支（详见下方"角色分支"）。
4. 进入项目调用 goToProject(projectName)统一跳转项目详情页。

角色分支（核心规则）

  • 多个已认证角色（≥2）：弹出"选择加入角色"弹窗，列出被邀请人全部已认证角色；用户选择其一后，以该角色身份加入项目并进入项目详情页（轻提示"已以「角色」身份加入，正在进入..."）。
  • 单一或无已认证角色（≤1）：无需选择，直接以默认身份加入并进入项目详情页（轻提示"已加入项目，正在进入..."）。

交互要点

  • 取消选择：角色选择弹窗可"取消"，取消后停留在消息列表，消息仍为"已接受"状态，可后续从卡片再次进入项目。
  • 身份归属与默认权限：被邀请人若为服务人员（member_category=service），接受后落库成员记录默认权限 permission_level=basic（仅基础公开数据、无治理权限），与 7.6 默认权限规则一致。
  • 业主类不受限：被邀请人为业主 / 业主家人（member_category=owner）时，不受"多角色选择"约束，直接进入项目且默认获得全部权限（permission_level=full）。
  • 一致性：本规则与 7.5（平台内选择需已认证至少一个角色方可被匹配）、7.6（身份分段与默认权限）共同构成完整的邀请能力，三端（服务方 / 业主小程序、PC 管理端）接收逻辑保持一致。
说明

"已认证角色"指用户在平台已完成认证的角色（如水电工、木工、项目经理等），数量来源于 users.certified_role_count。仅当数量 ≥ 2 时触发角色选择，避免单角色 / 无角色用户产生多余操作步骤。

7.8 合同邀约消息（来自 ContractStore）

服务方"合同邀约" Tab 的数据由 ContractStore 提供：每创建一份工人合同并向被邀请人发出邀约时，由 ContractStore.addMessage 生成一条 type=contract_invite 消息（字段见 7.4.2）。其生成、确认（并发首胜）、撤回、抢单失败的底层逻辑归口《PRD-合同模块详细规格》服务方小程序工人合同章节（#page-mini-service，3.7–3.13），消息页仅负责：

  • 按 status 渲染状态徽标与"查看邀约"跳转（见 7.5.2 / 7.6）；
  • 未读角标计算与"全部已读"清理（与邀请消息一并 markAllRead）；
  • 运行时数据迁移：自动将旧 localStorage 中残留的"陈业主"修正为"陈庄（工长）"；
  • 首次进入由 ensureContractInviteDemo 注入示例并强制对齐合同底层状态，保证卡片与合同详情视角一致。
7.9 数据来源与持久化
  • 邀请消息：本地内存示例数据（messages 对象），演示用，刷新后重置；未读态在会话内维护。
  • 合同邀约消息：持久化于 localStorage（ContractStore），跨会话保留；首次进入由示例脚本注入 6 条覆盖 查看邀约 / 已撤回 / 已拒绝 / 抢单失败 / 已确认 五类效果的示例。
  • 未读同步：邀请消息未读在会话内维护；合同邀约未读持久化于 ContractStore，markAllRead 一并清除两类未读并刷新角标。
7.10 服务通知（微信订阅消息）

定位：服务通知是平台在微信客户端层的触达通道——用户离开小程序时，平台通过微信合规通道（订阅消息）向用户微信的「服务通知」会话推送提醒；用户点开通知即直达小程序内对应页面（含状态视角参数）。它与消息页（站内聚合，见 7.1~7.9）、「待办」（站内任务归口，见《PRD-任务模块详细规格》）三者互补：消息页承载站内消息列表，待办承载站内任务处理，服务通知负责站外及时触达。

与站内能力的边界：

  • 服务通知不占用站内消息页 Tab（消息页仅 邀请 / 合同邀约，见 7.3）；推送记录留存于微信「服务通知」会话，平台侧不提供站内通知列表回看。
  • 任务类提醒（如确认人驳回 → 执行人重新执行）站内不生成待办，执行人提醒统一走服务通知（触发规则详见 PRD-任务模块详细规格 §3.12 / §3.15(5)）。
  • 推送须符合微信订阅消息合规要求（用户订阅一次、推送一条；模板字段受平台审核约束）。
